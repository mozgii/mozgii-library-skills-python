# Python projects with uv

uv is Astral's Python package and project manager. One binary replaces pip, virtualenv, pip-tools, pipx and pyenv: it installs Python versions, resolves a cross-platform lockfile (`uv.lock`), keeps `.venv` in sync with it, and runs commands inside it. This skill covers projects; single-file scripts, tools and CI live in its reference files.

## Step 0: read the installed version

uv changes quickly (0.13 made Python 3.15 the default and changed `uv init`), so read the version and its changelog before relying on any flag.

```bash
uv --version                      # e.g. uv 0.13.6
uv self update                    # standalone installs only; Homebrew: brew upgrade uv
uv python list --only-installed
```

Install uv with `curl -LsSf https://astral.sh/uv/install.sh | sh` (macOS, Linux), `powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"` (Windows), `brew install uv`, or `pipx install uv`. Pin the version in CI (see [ci-and-docker.md](references/ci-and-docker.md)).

## Which uv workflow fits this folder

uv has four ways of working, and the files already present say which one to use. Check them before running anything, because the wrong one leaves changes the next `uv sync` undoes.

| You find | Work this way | Why the alternatives lose |
|---|---|---|
| `uv.lock`, or a `pyproject.toml` you own | project: `uv add`, `uv sync`, `uv run` | `pip install` and `python -m venv` change `.venv` behind the lock, and the next sync removes them |
| one `.py` file to run | script: `uv run file.py`, `uv add --script file.py httpx` | a project around one file adds a lock and a venv to look after |
| a command such as Ruff or a release helper | tool: `uvx ruff`, or `uvx ruff@0.17.3` for a known version | `uv tool install` keeps a global copy to maintain; use it only when you want the command on `PATH` for good |
| `requirements*.txt` headed "autogenerated by uv", and no `uv.lock` | pip interface: `uv pip compile`, `uv pip sync` | starting a second set of requirements files inside a uv project splits the source of truth |
| `poetry.lock` or `pdm.lock` | leave it to that tool, unless the job is to migrate | uv does not read those locks, so mixing tools produces two answers to what is installed |

Inside a project, run Python through uv rather than directly: `uv run python -c "..."` sees the project's packages, while a bare `python` may be any interpreter on `PATH`. For one command on another version without a project, `uvx python@3.14 -c "..."` fetches that Python.

## Create a project

`uv init` writes `pyproject.toml`, `.python-version`, `README.md`, `.gitignore` and a git repository. Since uv 0.12 the default is a packaged project with a `src/` layout and the `uv_build` backend.

```bash
uv init my-app                  # packaged app: src/my_app/__init__.py, [project.scripts] my-app = "my_app:main"
uv init --lib my-lib            # library: src/my_lib/, py.typed, no script entry
uv init --no-package my-tool    # flat main.py, no build system: the project itself is not installed
uv init --python 3.13 my-app    # pin the Python version at creation
uv init --bare                  # only pyproject.toml, for an existing folder
```

The packaged layout lets tests import the package, lets other projects depend on it, and makes `uv run my-app` work. Use `--no-package` only for a folder of scripts that will never be imported elsewhere.

```toml
# pyproject.toml written by `uv init my-app` (uv 0.13)
[project]
name = "my-app"
version = "0.1.0"
description = "Add your description here"
readme = "README.md"
authors = [{ name = "Ada Lovelace", email = "ada@example.com" }]   # from your git identity, when set
requires-python = ">=3.15"
dependencies = []

[project.scripts]
my-app = "my_app:main"

[build-system]
requires = ["uv_build>=0.13.6,<0.14.0"]
build-backend = "uv_build"
```

`requires-python` follows the Python uv picks for the project: `>=3.15` here, with 3.15 available. Lower it to the oldest version you really support; libraries usually support the oldest Python still in security support (3.11 in late 2026).

## Python versions

uv downloads managed CPython builds and records the project's choice in `.python-version`.

```bash
uv python install 3.14 3.13         # managed builds into uv's data dir
uv python install 3.14t             # free-threaded build (no GIL), Python 3.14+
uv python pin 3.14                  # writes .python-version in this folder
uv python pin --global 3.14         # default for every project without a pin
uv python install 3.14 --default    # also puts python and python3 commands on PATH
uv python list                      # installed and downloadable versions
uv python upgrade 3.14              # newest patch release of an installed minor
uv run --python 3.13 pytest         # one-off run on another version
```

- `requires-python` says what the project supports; `.python-version` says what developers and CI use. The pin must satisfy `requires-python`.
- uv prefers managed Pythons; `--managed-python` or `UV_MANAGED_PYTHON=1` requires them, `--no-managed-python` uses system ones only.
- `UV_PYTHON_DOWNLOADS=never` stops automatic downloads (air-gapped CI).

## Dependencies

`uv add` edits `pyproject.toml`, updates `uv.lock` and syncs `.venv` in one step. Never edit the dependency lists by hand and forget the lock.

```bash
uv add httpx "pydantic>=2.12"               # runtime dependencies
uv add --dev pytest ruff pyright            # the "dev" dependency group (PEP 735)
uv add --group docs mkdocs-material         # another group
uv add --optional cli typer                 # an extra: pip install my-app[cli]
uv add "psycopg[binary]"                    # a package extra
uv add "my-lib @ git+https://github.com/org/my-lib@v1.2.0"
uv add --editable ../my-lib                 # local path, editable
uv add --bounds minor rich                  # writes "rich>=15.0.0,<15.1.0" instead of "rich>=15.0.0"
uv remove httpx
```

| Kind | Where it lands | Installed by |
|---|---|---|
| runtime dependency | `[project] dependencies` | everyone, including users of the published package |
| dev tools (tests, linters) | `[dependency-groups] dev` | `uv sync` by default, never published |
| other groups (docs, bench) | `[dependency-groups] <name>` | `uv sync --group <name>` or `--all-groups` |
| optional feature | `[project.optional-dependencies] <extra>` | `uv sync --extra <extra>`, users via `my-app[extra]` |

Use dependency groups, not extras, for development tools: extras are published metadata that users can install.

## Lock and sync

`uv.lock` is a universal lockfile: one file resolves for every OS, architecture and Python version the project allows. Commit it.

```bash
uv lock                          # resolve and write uv.lock (keeps existing versions when possible)
uv lock --check                  # CI: fail if pyproject.toml changed without a new lock
uv lock --upgrade                # move every package to its newest allowed version
uv lock --upgrade-package httpx  # move one package
uv sync                          # make .venv match uv.lock exactly (removes extras not in the lock)
uv sync --locked                 # fail instead of updating an out-of-date lock (CI)
uv sync --frozen                 # use the lock as is, without checking it against pyproject.toml
uv sync --no-dev                 # production install
uv sync --all-groups --all-extras
uv sync --inexact                # keep packages that are not in the lock
```

- `--locked` asserts the lock is current; `--frozen` skips the check. CI and Docker use `--locked`, so a stale lock fails loudly.
- `uv run` locks and syncs implicitly before running; `uv run --locked` and `uv run --frozen` behave like the sync flags.
- `uv pip install` into the project venv changes `.venv` but not the lock; the next `uv sync` removes it. Use `uv add`.

## Run commands

`uv run` runs a command inside the project environment without activating it.

```bash
uv run pytest -q
uv run python -m my_app
uv run my-app --help                   # a [project.scripts] entry point
uv run --with rich python demo.py      # add a package for this run only
uv run --isolated --with pytest pytest # a throwaway environment
uv run --package my-lib pytest         # one member of a workspace
```

Activating still works (`source .venv/bin/activate`, `.venv\Scripts\activate` on Windows), but `uv run` keeps the lock and environment in sync on every call.

## Inspect and upgrade

Inspect the tree before upgrading, and upgrade in small steps.

```bash
uv tree                                # full dependency tree
uv tree --outdated --depth 1           # direct dependencies with newer versions available
uv tree --invert --package urllib3     # who depends on urllib3
uv lock --upgrade-package pydantic && uv run pytest -q
uv version                             # project version
uv version --bump minor                # 0.1.0 => 0.2.0 in pyproject.toml
```

## Workspaces

A workspace is several packages in one repository that share one `uv.lock` and one `.venv`.

```toml
# pyproject.toml at the repository root
[project]
name = "my-app"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = ["my-core"]

[tool.uv.workspace]
members = ["packages/*"]

[tool.uv.sources]
my-core = { workspace = true }         # resolve my-core from packages/my-core, editable
```

```bash
uv init --lib packages/my-core         # inside a workspace, uv adds it to members
uv sync --all-packages                 # install every member
uv run --package my-core pytest
uv workspace list                      # member names and paths
```

- Members share one resolution: two members cannot pin conflicting versions of a dependency. Packages that must disagree belong in separate projects (or declare `[tool.uv] conflicts` between extras).
- Use path dependencies (`{ path = "../other", editable = true }`) instead of a workspace when the projects need separate locks.

## Package indexes and sources

`[tool.uv.sources]` says where a dependency comes from; `[[tool.uv.index]]` declares extra indexes.

```toml
[[tool.uv.index]]
name = "internal"
url = "https://pypi.example.com/simple"
explicit = true                        # only packages that name this index use it

[tool.uv.sources]
my-private-lib = { index = "internal" }
```

- Credentials come from the environment, never the file: `UV_INDEX_INTERNAL_USERNAME` and `UV_INDEX_INTERNAL_PASSWORD` (the index name upper-cased), `uv auth login pypi.example.com`, or keyring.
- `explicit = true` prevents dependency confusion: a public package with the same name cannot replace the private one.
- uv refuses more than one index with `default = true`, and since 0.10 an `explicit` index must have a name.

## Reproducible resolution

`exclude-newer` ignores every file uploaded after a date, so a lock made today and a lock made next month resolve the same way.

```toml
[tool.uv]
exclude-newer = "7 days"               # or a date: "2026-10-01"; a rolling window also delays fresh malicious uploads
exclude-newer-package = { my-private-lib = false }   # exempt one package
```

Pair it with `uv lock --check` in CI. For hash-checked installs outside uv, export with hashes: `uv export --format requirements.txt --no-dev --no-emit-project -o requirements.txt`.

## Export and the pip interface

Export the lock for tools that do not read `uv.lock`, and use `uv pip` where a project is not wanted.

```bash
uv export --format requirements.txt --no-dev --no-emit-project -o requirements.txt   # pinned, with hashes
uv export --format pylock.toml -o pylock.toml                      # PEP 751 lockfile
uv export --format cyclonedx1.5 -o sbom.json                       # software bill of materials
uv venv --python 3.14                    # plain venv; --clear to replace an existing one
uv pip install -r requirements.txt       # pip-compatible, into the active or .venv environment
uv pip compile requirements.in -o requirements.txt --universal
uv pip sync requirements.txt             # make the env match exactly
```

## Migrate an existing project

Migration moves the dependency lists into `pyproject.toml` and lets uv produce the lock.

1. Without a `pyproject.toml`: `uv init --bare` (or `uv init --no-package` for an app folder).
2. From requirements files: `uv add -r requirements.txt` and `uv add --dev -r requirements-dev.txt`. Each line keeps its constraint: `idna==3.10` stays an exact pin in `dependencies`, and `six>=1.16` stays a lower bound. Loosen pins you do not need before a library publishes them.
3. From Poetry or Pipenv: `uvx migrate-to-uv` converts the metadata, groups and sources; review the diff, then `uv lock`.
4. Delete the old lock (`poetry.lock`, `Pipfile.lock`) and the old venv, run `uv sync`, run the tests.
5. Replace `pip install`/`poetry run` in CI and docs with `uv sync --locked` and `uv run`.

The everyday commands of the older tools map one to one, so habits and CI scripts translate directly.

| Old tool | Old command | uv command |
|---|---|---|
| pyenv | `pyenv install 3.14` | `uv python install 3.14` |
| pyenv | `pyenv versions` | `uv python list --only-installed` |
| pyenv | `pyenv local 3.14` | `uv python pin 3.14` |
| pyenv | `pyenv global 3.14` | `uv python install 3.14 --default` |
| pipx | `pipx run black` | `uvx black` |
| pipx | `pipx install black`, `pipx upgrade black` | `uv tool install black`, `uv tool upgrade black` |
| pipx | `pipx list` | `uv tool list` |
| pip | `pip freeze` | `uv pip freeze` |
| pip-tools | `pip-compile`, `pip-sync` | `uv pip compile`, `uv pip sync` |
| virtualenv | `virtualenv .venv` | `uv venv` |

## Experimental commands

Three newer commands work but print an experimental warning in uv 0.13; do not build CI on their exact output yet.

| Command | Does | Stable alternative |
|---|---|---|
| `uv format` | runs Ruff's formatter (downloads a pinned Ruff) | `uv run ruff format` with Ruff in the dev group |
| `uv check` | syncs the project, then runs Astral's `ty` type checker; takes `--fix` and `--ty-version` | `uv run ty check` with ty in the dev group (the `ty` skill), `uv run pyright` or `uv run mypy` |
| `uv audit` | checks the lock against the OSV vulnerability database | `uvx pip-audit` on an exported requirements file |

Silence the warning on purpose with `--preview-features format-command` (and `check-command`, `audit-command`).

## Verify

Prove that the lock, the environment and CI agree. A dependency planted behind the lock's back must make the check fail.

```bash
uv --version                                 # matches the pin in CI
uv lock --check; echo "exit $?"              # expect exit 0
uv sync --locked; echo "exit $?"             # expect exit 0
uv run python -c "import sys; print(sys.prefix)"   # the project's .venv
git ls-files uv.lock .python-version         # expect both
git check-ignore .venv                       # expect .venv
sed -i.bak 's/^dependencies = \[/dependencies = ["idna",/' pyproject.toml
uv lock --check; echo "exit $?"              # expect a stale lock message and exit 1
mv pyproject.toml.bak pyproject.toml
```

## Anti-patterns

| Instead of | Do |
|---|---|
| `pip install` or `uv pip install` in a project | `uv add`, so the lock follows |
| `uv sync` in CI | `uv sync --locked`, so a stale lock fails |
| `--frozen` in CI | `--locked`; `--frozen` skips the check |
| dev tools as extras | `[dependency-groups]` |
| `uvx pytest` for a project's tests | `uv run pytest`, which sees the project's packages |
| `setup-uv@v10` | an exact tag such as `@v10.3.3`; no major tag exists |

## Checklist

A project is set up when every item holds.

- [ ] `pyproject.toml` has `requires-python` matching what you test; `.python-version` is committed.
- [ ] `uv.lock` is committed; CI runs `uv lock --check` and `uv sync --locked`.
- [ ] Dev tools live in `[dependency-groups]`, not in `dependencies` or extras.
- [ ] Private indexes are `explicit = true`; credentials come from environment variables.
- [ ] Nobody runs `uv pip install` into the project venv; changes go through `uv add`/`uv remove`.
- [ ] `.venv/` is in `.gitignore`.

## Gotchas

These are the uv behaviours that surprise people.

1. **`VIRTUAL_ENV=... does not match the project environment path .venv and will be ignored`.** Another venv is activated in the shell. uv uses the project's `.venv` anyway; deactivate it, or pass `--active` to target the activated one on purpose.
2. **A package vanished after `uv sync`.** It was installed with `uv pip install` or `pip install` and is not in the lock; sync is exact. Add it with `uv add`.
3. **CI resolves a different version than your laptop.** CI ran `uv sync` without `--locked` and updated the lock, or the lock was never committed. Commit it and use `--locked`.
4. **`uv init` made a `src/` package when you wanted a script folder.** That is the default since 0.12; use `--no-package`.
5. **`uv venv` fails on an existing `.venv`.** Since 0.10 it needs `--clear` to replace it.
6. **A `uv_build` upper bound blocks building after a uv upgrade.** `requires = ["uv_build>=0.13.6,<0.14.0"]` stops working with uv 0.14's backend pin; raise the bound when you upgrade uv.
7. **Two workspace members need different versions of a library.** One workspace has one resolution. Split them into separate projects or declare conflicting extras.
